# Taskmaster S0 评审议题

评审对象：[PRD v0.1](../prd/taskmaster-prd.md) ｜ [设计 v0.1](../design/taskmaster-design.md) ｜ 上游 [需求池 v2.0](../requirement/taskmaster-requirements.md)。
评审出口：4 条开放问题逐条裁决（或定负责人+48 小时裁定）；三件套转 approved；owner/reviewers 落定。

## 议题一：确认闸的交互形态

- **背景**：每次派发前出计划卡等人确认（FR-4），是成本与安全的唯一控制点；形态决定"烦不烦"（最危险假设）。
- **选项 A**：计划卡投属主会话等 confirm——零新组件，属主窗口即审批台；缺点：属主窗口关着时只能排队补投。
- **选项 B**：独立审批 UI——体验好、可批量；缺点：M1 范围外的新增前端面，排期 +1~2 周。
- **倾向**：**A**（一期），B 列为二期增强；用驳回率指标（阈值 30%）验证 A 够不够。
- **要谁拍板**：需求方 + 评审会。

## 议题二：验收的机械边界

- **背景**：checks 里哪些引擎能机械核验（文件存在/命令退出码/测试通过），哪些必须人看（"设计合理"类）。边界划错 = 要么打回太狠，要么验收形同虚设。
- **选项**：A 白名单制（只机械核验可证伪条目，其余人看）/ B 全机械 + 人工抽查兜底。
- **倾向**：**A**；图 schema 里 checks 条目声明 `verify: mechanical|human`，注册期校验机械条目的可执行性。
- **要谁拍板**：需求方（影响图怎么写）。

## 议题三：心跳节拍时长与 TTL

- **背景**：节拍快 = 空转烧 CPU；节拍慢 = stalled 误报/晚报。3 任务图与 300 任务图不该共用一拍。
- **选项**：A 全局固定配置 / B 按图可配。
- **倾向**：折中——**全局默认 + 图级可选覆盖 + 上下限钳制**（配置结构预留图级字段，S1 先只实现全局默认）。
- **要谁拍板**：评审会；S1 开工前必须定初值。

## 议题四：执行者来源

- **背景**：FR-10 投递的任务包发给谁。每次 spawn 新 agent（干净、隔离好、冷启动贵）vs 执行者池注册认领（复用、暖，但引入认领竞争与回收——正是 R-14 延期的理由）。
- **倾向**：**A 每次 spawn**（一期），池化与 R-14 拉模式二期合并评审。
- **要谁拍板**：评审会；此题截止 S2 前（2026-11-08），不阻塞 S1 开工。
