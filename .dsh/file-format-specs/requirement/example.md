# 文件规范插件 需求池

## 摘要

- **要解决什么**：项目想约束文档结构，但判据写死在插件代码里，只能退化成 prompt 里的一句叮嘱。
- **来源与证据强度**：3 人访谈 + 42 份文档返工记录 + 6 条被「要改插件」挡住的判据清单，证据集中且可复核。
- **本轮结论**：8 条需求中 6 条已进 PRD（R-1～R-6），1 条明确拒绝（R-7），1 条延期（R-8）。

## 背景与来源

- **收集方式**：试点项目回访（半结构化访谈 3 人，各 45 分钟）+ 台账统计（3 周内 42 份文档的返工次数）+ 需求方自己列的判据清单（6 条）。时间范围 2026-09-22 ～ 2026-10-07。
- **样本**：3 名项目维护者、2 名评审人、1 名插件维护者；覆盖 2 个试点项目。
- **原始记录**：访谈纪要 `docs/notes/2026-10-pilot-interviews.md`；返工台账见 PRD 示例的「影响与证据」一节。

## 干系人与角色

| 角色 | 关注点 | 影响程度 | 决策权 |
|---|---|---|---|
| 项目维护者 | 判据能不能改成自己的；改完成本多高 | 高 | 决策（是否在本项目启用） |
| agent | 被打回后能不能一轮改对 | 高 | 建议（反馈可读性） |
| 评审人 | 评审时间别被结构问题吃掉 | 中 | 建议 |
| 插件组 | 引擎抽象是否值得；误报是否可控 | 高 | 决策（是否实现） |

## 待解问题

| 问题 | 证据 | 影响 | 谁受影响 |
|---|---|---|---|
| 项目特有的文档规范无处表达 | 6 条判据全部因「要改插件」搁置 | 规范只能靠 prompt，无法机械验证 | 项目维护者、评审人 |
| 校验只报缺什么、不报改成什么样 | 同一份需求平均写 2.3 次；PRD 因缺验收标准被打回 17 次 / 42 份 | agent 反复试错，上下文与时间被吃掉 | agent、评审人 |
| 新增判据＝改代码＋发版 | 判据改动需要构建、安装、重启，回归风险高 | 没人敢加判据，规范长期停留在初始版本 | 插件组、项目维护者 |
| 存量文档结构不齐 | 试点已有 200+ 份存量文档，其中约三成缺必备章节 | 若全量追溯会产生上千条历史违规，直接压垮新机制 | 项目维护者 |

## 假设与风险

| 假设 | 如果错了会怎样 | 证伪方式 | 结论 |
|---|---|---|---|
| 如果判据可配置，那么项目方会自己维护 spec.yaml，因为改 YAML 比改代码便宜 | 整件事的价值归零——产品退化成又多一份没人维护的配置 | 2 周内统计「自建 spec 的项目数 ≥ 2」 | 未验证 |
| 如果打回文本给出目标形状，那么 agent 一次修复率会从 43% 提到 80% 以上 | 反馈链路白做，agent 仍靠猜 | 6 份真实被打回文档做修复演练，记录下一次 write 即零 error 的比例 | 未验证 |
| 如果判据只判机器能证伪的结构事实，那么误报率会低于 5% | 误报侵蚀信任，维护者会直接把 mode 关掉 | 试点 warn 期统计误报率 | 未验证 |
| 如果校验只读落盘后的全文、不写文件，那么在插件里做校验不会影响宿主写入 | 需要改成独立进程或异步校验，架构与里程碑都要重排 | 集成测试覆盖 accept / block / 放行三态 | 成立 |

## 需求清单

| 编号 | 需求陈述 | 类型 | 优先级 | 状态 |
|---|---|---|---|---|
| R-1 | 项目维护者要能自己声明本项目的文档判据，不必改插件代码或等发版 | 约束 | Must | 已进 PRD |
| R-2 | 判据要能表达跨行、跨节的结构约束（如「每个 H2 都要带标注」「清单编号必须在明细里出现」） | 功能 | Must | 已进 PRD |
| R-3 | 同一条判据在多处重复计算时应该能复用，而不是各写一遍 | 约束 | Should | 已进 PRD |

| R-5 | agent 被打回后必须知道「改成什么形状」，而不只是「缺了什么」 | 质量属性 | Must | 已进 PRD |

| R-8 | PRD 的指标名与指标方案必须一一对应（跨文档一致性） | 功能 | Could | 已延期 |

## 需求明细

#### R-1 判据可配置

**描述**

项目在自己的工作区里放一份 spec.yaml 声明文档结构与内容判据，插件按它校验；新增或修改判据只改 YAML，不碰插件代码、不需要发版或重启会话。

**来源与证据**

维护者访谈 3/3 提到「判据改不了」；需求方给出的 6 条自定义判据全部标注理由「要改插件，先搁置」，清单见访谈纪要附录 B。

**验收判据**

改 spec.yaml 并保存后，下一次 write/edit 即按新规则校验（无需重启）；一份非法 spec 只影响它自己那个类型，其它类型照常校验。

**优先级理由**

Must：不做则产品价值为零——项目只能用 prompt 表达规范，而 prompt 无法机械验证。它是 R-2 / R-4 的载体。

#### R-2 跨行跨节的结构判据

**描述**

判据要能表达「每个 H2 都必须带 serves 标注」「清单里的每个编号都必须在明细里出现」这类跨行、跨节的约束，并且报错要能定位到行号。

**来源与证据**

维护者列出的 6 条判据里 5 条属结构类（章节齐全、编号连续、表格列齐、章节标注、清单与明细对齐）；访谈中明确表示「正则整篇匹配做不到『每一个』」。

**验收判据**

用条件树（each + where）或内置原语表达「每个 H2 必须带 serves」，违反时报出对应行号；清单有编号但缺明细时能被拦下。

**优先级理由**

Must：结构判据是这 6 条诉求的主体；只做「可配置」而做不出结构判据，等于没解决。

#### R-3 判据计算可复用

**描述**

同一份 spec 里被多条规则反复用到的计算结果（如「本文有多少条 FR 编号」）应该只算一次并可命名复用，避免每条规则各写一遍、写法还不一致。

**来源与证据**

需求文档 spec 起草时，有 3 条规则都要数 FR 编号；维护者反馈「抄来抄去，改一处漏两处」。

**验收判据**

派生事实后，规则可直接按事实名判断（如 `[requirementCount ≥ 1]`）；派生链后一条能看见前一条。

**优先级理由**

Should：不做也能写出来，只是重复且容易漂移；它降低的是维护成本，不阻断上线。

**依赖与假设**

依赖 R-2 的条件树先可用。

#### R-4 自定义判据逃生舱

**描述**

内置原语覆盖不到时，项目能在 spec 里写一小段判据逻辑（表达式或脚本），并保证它写坏时不会拖垮整次校验。

**来源与证据**

6 条搁置判据里有 2 条不属于任何内置原语：「术语表必须覆盖正文出现的缩写」「日期一律用 YYYY-MM-DD」。

**验收判据**

在 functions 里写 expr/script 后生效；脚本死循环被超时截断并只产出一条失败，其余规则照常执行。

**优先级理由**

Should：只影响少数项目；但它是「不必改插件」这个承诺的最后一块拼图，砍掉就要重新解释哪些判据做不了。

**不做的后果**

那 2 条判据只能继续搁置，维护者会认为「可配置」是半个承诺。

#### R-5 打回时给出目标形状

**描述**

校验失败时，反馈里除了「缺什么」，还要给出目标模板（或按规则反推的骨架）、填写参考的位置、以及剩余可修复次数。

**来源与证据**

3 周 42 份文档中 17 份 PRD 因「缺验收标准」被打回；同一份需求平均要写 2.3 次才过结构校验。评审人访谈：「结构问题占了评审时间的三分之一。」

**验收判据**

block 文本包含本次新增违规（带行号与建议）、历史违规计数、目标模板或骨架、填写参考路径、剩余次数；agent 下一次 write 即零 error 的比例达 80% 以上。

**优先级理由**

Must：它是 R-1 到「省时间」之间的唯一通道——判据再多，agent 改不对就没有收益。

#### R-6 存量文档豁免

**描述**

只拦本次操作新增的问题，不追溯文件里已有的历史违规；新建文件时按严格口径校验。

**来源与证据**

试点已有 200+ 份存量文档，抽查约三成缺必备章节；若全量追溯，首次启用就会产生上千条违规，维护者会直接关闭校验。

**验收判据**

同一份文档在 before 中已有的违规不计入本次结果；新建（无 before）时等价严格校验。

**优先级理由**

Must：不做则新机制无法在存量项目启用——这是「能不能上线」的门槛，不是体验优化。

#### R-7 机器评审表达质量

**描述**

希望校验能判断「这段话写得好不好、清不清楚」，把评审人从文字问题上也解放出来。

**来源与证据**

2 位评审人提出；但同 3 位评审人也都承认「主要时间消耗在结构问题，不是文字质量」。

**验收判据**

不适用——本期明确不做。主观质量的判据无法机械证伪，误报会直接侵蚀对整套校验的信任。

**优先级理由**

Won't：收益不确定、误报成本高，且会与「只判机器能证伪的结构事实」这条设计纪律冲突。需要时由评审流程解决，不进引擎。

#### R-8 跨文档口径一致性

**描述**

校验同一批文档之间的口径一致性，例如 PRD 里的指标名必须在指标方案里存在、编号必须对得上。

**来源与证据**

上一轮出现 1 次口径分叉：PRD 写「一次修复率」，指标方案叫「修复成功率」，两边对不上。

**验收判据**

待下一期定义——需要跨文件解析、编号对齐与「以哪边为准」的仲裁规则。

**优先级理由**

Could：发生频次低（约 1 次/季度），且实现成本明显高于单文档校验；本期先把单份文档的形状做扎实。

**不做的后果**

偶尔出现两份文档口径不一致，需人工在评审时发现；不影响本期上线。

## 优先级与排序

| 排序方法 | 判据 | 本轮结论 |
|---|---|---|
| MoSCoW | Must = 不做则产品不成立；Should = 影响效率或维护成本；Could = 有价值但成本明显更高；Won't = 本期明确不做 | Must：R-1 / R-2 / R-5 / R-6（前两条决定「能不能配置」，后两条决定「能不能落地」）；Should：R-3 / R-4；Could：R-8；Won't：R-7 |
