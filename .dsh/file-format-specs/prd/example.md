# 内容格式规则引擎 PRD

## 摘要

把「文档内容该长什么样」从写死的检查代码变成**可配置的规则数据**：项目在
.dsh/file-format-specs/<type>/spec.yaml 里声明规则，插件在 write/edit 落盘后按规则校验，
合规静默放行、不合规一次报全并给出目标模板。目标是把「agent 写完文档总差几节」从反复返工压到一次改对。

## 发布公告

**标题**：让每个项目自己定义「文档该写成什么样」

**副标题**：面向用 DSH 写文档的项目——在项目里放一份 spec.yaml，agent 写的需求/PRD 自动按你的规范校验与纠偏，不合规不再靠人挑。

**客户问题**：文档规范只能写进 prompt，模型想遵守但记不住；等评审时才发现缺章节、缺验收判据，同一份要返工两三次。

**如释重负的一句话**：「改完 spec.yaml 就生效了，不用等插件发版，也不用再人肉挑格式。」

## 背景与问题

### 现状

文档质量目前靠两件事兜：一是写死在插件里的几种检查（缺章节、缺 front-matter 字段），
二是人工评审。项目想加一条自己的判据（例如「每条 FR 必须有验收判据」），必须改插件代码、重新构建。

### 问题

- 判据不可配置：项目特有的文档规范无法表达，只能写进 prompt 靠模型自觉；
- 检查与修复脱节：只报「缺章节」不给目标形状，agent 知道缺什么、不知道改成什么样；
- 误报漏报难定位：新增判据是代码改动，回归风险高，没人敢加。

### 影响与证据

- 试点项目 3 周内 PRD 因「缺验收标准」被打回：17 次 / 42 份；
- 同一份需求平均要写 2.3 次才能过结构校验；
- 项目方提出的 6 条自定义判据，因「要改插件」全部搁置。

## 目标与非目标

### 目标

- 让项目**不改代码**就能声明文档结构判据，改 YAML 即生效；
- 校验失败时给出**目标模板 + 差异清单**，agent 一轮改对；
- 判据可增量启用，旧文档不被追溯。

### 非目标

- 不做自然语言质量评审（「这段话写得好不好」）——机器判不了，交给评审；
- 不做跨文档全局一致性校验（本期只管单份文档的形状）；
- 不替换宿主 write/edit，只在 post-execute 上挂校验。

| 角色 | 场景 | 痛点 | 现状行为 | 期望行为 |

| 项目维护者 | 定义本项目的文档规范 | 判据写死在插件里，改不了 | 把要求写进 prompt | 在 spec.yaml 里声明规则 |

## 用户旅程与流程设计

### 参与者与触发条件

- **参与者**：宿主 write/edit、插件、agent、项目维护者。
- **触发条件**：write/edit 成功返回 after 全文。
- **前置状态**：文件已经落盘；插件可按相对路径匹配项目 spec。
- **结束状态**：合规时 accept 且零正文；warn/block 时返回差异与修复指引。block 只改变工具结果，不回滚已落盘内容。

### 主流程（ASCII 图）

```text
write/edit 成功（after 已落盘）
|
+-- 未命中 spec --> accept，零正文
|
+-- 命中 spec
    |
    +-- spec 非法 --> 记录 warning，跳过该类型 --> accept
    |
    +-- spec 合法 --> derive + rules
        |
        +-- 函数异常：记一条错误，继续其它规则
        |
        +-- 聚合违规，并按 diff_mode 归责
            |
            +-- 无新增 error --> accept
            |
            +-- 有新增 error
                |
                +-- mode=off   --> accept
                +-- mode=warn  --> accept + 警告与修复指引
                +-- mode=block --> block + 差异清单 + 目标结构 + 重试信息
                    |
                    +-- 尚有重试预算
                    |       agent 修复 --> write/edit --> 重新校验
                    |
                    +-- 重试耗尽
                        |
                        +-- on_exhausted=allow --> accept + 警告（仍可能不合规）
                        +-- on_exhausted=block --> 保持 block，等待人工处理
```

### 状态与结果对照表

| 场景 | 触发 / 操作 | 系统结果 | 用户反馈 | 下一步 |
|---|---|---|---|---|
| 未命中 spec | write/edit 成功 | accept；文件已写入 | 零正文 | 结束 |
| 合规或 delta 后无新增 error | 校验完成 | accept；文件已写入 | 零正文或历史建议 | 结束 |
| spec 非法 | 加载 spec | 跳过该类型；文件已写入 | warning 指向 spec，不伪报文档违规 | 维护者修 spec |
| mode=warn 且有新增 error | 校验完成 | accept；文件可能仍有违规 | 警告 + 修复指引 | 决定是否修复 |
| mode=block 且有新增 error | 校验完成 | block；文件已写入但不合规 | 差异 + 目标结构 + 剩余次数 | agent 修复 |
| 重试耗尽且 allow | 再次提交仍不合规 | accept 放行；文件可能仍不合规 | 明确「已放行但未通过」 | 人工复查 |
| 重试耗尽且 block | 再次提交仍不合规 | 保持 block；文件仍不合规 | 提示人工介入 | 人工处理 |

### 异常与恢复路径

- spec 缺失 → 不校验并静默放行；spec 非法 → 告警并提示维护者修复配置。
- 自定义函数抛错或超时 → 记录函数执行失败，继续其它规则；依赖失败事实的规则按既定错误策略处理。
- 同一 after 重复提交 → 提示「内容未变，仍不符合」，避免无效重试。
- 重试耗尽 → 明确区分「零 error 通过」与「on_exhausted=allow 放行」，后者仍须人工复查。

## 原型与交互说明

- **涉及页面**：否。
- **原型链接**：不适用——本产品无新增或修改页面。
- **覆盖范围**：agent 在 write/edit 后接收的 accept / warn / block 文本反馈。
- **原型版本 / 日期**：文本原型 v1 / 2026-10-14。
- **访问说明**：原型内联在本文件，无外部链接依赖。
- **覆盖状态**：静默通过、普通 block、历史违规 delta、spec 非法、重试耗尽。
- **文字替代**：流程见上一节；反馈字段与异常语义见 FR-6 和「边界与异常路径」。

## 功能需求

### 需求清单

| 编号 | 需求 | 优先级 | 验收判据 |
|---|---|---|---|
| FR-1 | 维护者在类型目录的 spec.yaml 声明规则，无需改插件即可生效 | Must | 改 spec.yaml 保存后，下次写文档即按新规则校验，无需重启 |
| FR-2 | 引擎以「事实 + 条件树」求值：all/any/not/path/each/exists/count/fn | Must | 用 each + where 表达「每个 H2 必须带 serves」，违反时报出对应行号 |
| FR-3 | 支持前向链 derive，把重复计算变成事实 | Should | 派生 requirementCount 后，规则可直接用 [requirementCount ≥ 1] 判定 |
| FR-4 | 内置原语（sectionsRequired/tableRequired/ids/idDetails 等）以 fn 形式调用 | Must | { fn: sectionsRequired, args: [{headings:[…]}] } 缺节即报 |
| FR-5 | 允许在 functions 里写 expr/script 自定义判据，沙箱加超时 | Should | 死循环脚本被 1s 超时截断并报一条错误，不影响其它规则 |
| FR-6 | 校验失败时输出目标模板与差异清单 | Must | 没有模板时按规则反推目标结构，block 文本含「目标结构」小节 |

### 需求明细

#### FR-1 spec.yaml 声明即生效

**优先级**：Must ｜ **角色**：项目维护者 ｜ **依赖**：无

**描述**

规则以项目内的文件为载体：每个类型目录一份 spec.yaml，插件校验时按目录读取并缓存。用户改文件即生效，插件不需要重新发版。

**业务规则**

- BR-1.1 每个类型目录（目录名即类型名）下一份 spec.yaml，含 match 与 rules。
- BR-1.2 rules/derive/functions 三块都可选，缺省即无对应判据。
- BR-1.3 缓存按 spec.yaml 与 template.md/example.md 的 mtime 失效。

**验收标准**（Given / When / Then）

- AC-1.1 Given 已有一个类型目录，When 修改其 spec.yaml 并保存，Then 下一次 write/edit 按新规则校验，无需重启。
- AC-1.2 Given spec.yaml 语法非法，When 触发校验，Then 记一条 warning 并跳过该类型，其它类型照常。

**异常与边界**

- spec.yaml 缺失 → 该类型完全不受约束，静默放行。

**不在本期范围**

- 不做 spec 的可视化编辑器，不做 IDE 插件。

#### FR-2 条件树求值

**优先级**：Must ｜ **角色**：项目维护者 ｜ **依赖**：FR-1

**描述**

引擎把文档铺成事实集合，条件树在其上递归求值。条件分四类：组合子、量词、叶子、函数调用。

**业务规则**

- BR-2.1 组合子语义：all 全过才过、any 一过即过、not 取反。
- BR-2.2 量词（each/exists/count）把作用域重绑到元素，元素行号冒泡到违规。
- BR-2.3 未知算子按 false；无法识别的条件报一条错误，绝不崩。

**验收标准**（Given / When / Then）

- AC-2.1 Given 一份 H2 缺 serves 的文档，When 跑 each + where + require，Then 报出缺标注的具体行号。
- AC-2.2 Given 条件里写了未知算子，When 求值，Then 该条判 false 且不抛异常。

**异常与边界**

- path 指向不存在的事实 → 返回 undefined；each/exists 目标不是数组 → 报一条错误。

**不在本期范围**

- 不做短路求值与缓存优化。

#### FR-3 前向链派生

**优先级**：Should ｜ **角色**：项目维护者 ｜ **依赖**：FR-2

**描述**

规则求值前先跑 derive，把重复计算固化成事实；后一条能看见前一条写入的事实。

**业务规则**

- BR-3.1 derive 支持 fn/expr/script/value 四种来源，按声明顺序执行。
- BR-3.2 派生结果写入事实集，规则用 path 读取。

**验收标准**（Given / When / Then）

- AC-3.1 Given 声明 requirementCount = countIds(["FR"])，Then 规则可直接写 path: requirementCount, op: gte。
- AC-3.2 Given 某条 derive 的函数抛错，Then 该条记一个错误，其余规则照常。

**异常与边界**

- fact 名为空 → 该条跳过；重复派生同名事实 → 后者覆盖前者。

**不在本期范围**

- 不做跨文档派生。

#### FR-4 内置原语

**优先级**：Must ｜ **角色**：项目维护者 ｜ **依赖**：FR-2

**描述**

常见结构判据以纯函数内置，注册成引擎函数供 fn 调用。参数是一个对象，结构类判据按归一化节名精确匹配、只认 H2。

**业务规则**

- BR-4.1 原语签名统一为 (doc, params)，yaml 里的 args[0] 即 params。
- BR-4.2 结构类原语按归一化节名精确匹配（去编号 / 括注 / serves）。
- BR-4.3 idDetails 校验「清单编号 ↔ 明细标题」，并可强制明细小节。

**验收标准**（Given / When / Then）

- AC-4.1 Given 文档缺一节，When 跑 sectionsRequired，Then 报「缺章节」并给出行号。
- AC-4.2 Given 清单有 FR-7 但无对应明细，When 跑 idDetails，Then 报「缺对应明细标题」。

**异常与边界**

- 参数缺省时按最小语义（如表头为空则只找表）；节名不匹配即报缺失。

**不在本期范围**

- 不做原语的插件外注册。

#### FR-5 自定义函数沙箱

**优先级**：Should ｜ **角色**：项目维护者 ｜ **依赖**：FR-2

**描述**

内置覆盖不到的判据用 expr/script 补。脚本在 node:vm 干净上下文执行，只注入白名单全局，默认 1s 超时。

**业务规则**

- BR-5.1 expr 返回布尔：为假则报 rule 的 message。
- BR-5.2 script 返回值归一化：undefined/null/true/[] 视为通过，string/对象/数组视为违规。
- BR-5.3 抛错只记一条「函数执行失败」，不阻断其它规则。

**验收标准**（Given / When / Then）

- AC-5.1 Given 脚本 while(true){}，When 执行，Then 1s 超时截断且只产出一条错误。
- AC-5.2 Given script 返回 [{message, line}]，Then 拆成带行号的违规。

**异常与边界**

- 访问白名单外的全局 → 抛错并记一条错误。

**不在本期范围**

- 不支持异步脚本。

#### FR-6 目标模板与差异清单

**优先级**：Must ｜ **角色**：agent ｜ **依赖**：FR-4

**描述**

block 时把「改什么」和「改成什么样」一起给出：目标结构优先用模板文件，其次从规则反推骨架，示例只给路径。

**业务规则**

- BR-6.1 目标优先级：template.md 全文 > 规则反推骨架 > 只给差异清单。
- BR-6.2 example.md 只输出路径指针，不内联正文。
- BR-6.3 一次报全所有新增违规，不第一条就停。

**验收标准**（Given / When / Then）

- AC-6.1 Given 一份缺章节的 PRD，Then block 文本含「【目标结构】」与缺失章节名。
- AC-6.2 Given 类型目录有 example.md，Then block 文本含「【填写参考】<路径>」。

**异常与边界**

- 模板缺失 → 退化为骨架；示例缺失 → 不打指针；推不出结构 → 只给差异清单。

**不在本期范围**

- 不做多候选目标的 A/B 推荐。

## 非功能需求

| 编号 | 类别 | 要求 | 优先级 |
|---|---|---|---|
| NFR-1 | 性能 | 单次校验 P95 ≤ 50ms（1000 行文档） | Must |
| NFR-2 | 可靠性 | 单份 spec 非法只跳过并告警，不影响其它类型校验 | Must |
| NFR-3 | 安全 | 用户脚本在 node:vm 白名单上下文执行，默认 1s 超时 | Must |
| NFR-4 | 隐私 | 校验只读 write/edit 结果里的 after 全文，不落盘、不外发、不留存 | Must |
| NFR-5 | 可观测性 | 每次 block 记一条结构化日志（spec 名 / 规则 id / 违规数），便于统计误报 | Should |
| NFR-6 | 兼容 | 旧文档不追溯：diff_mode=delta 只拦本次新增的违规 | Should |

## 边界与异常路径

- 目录里没有对应类型的 spec：不校验，静默放行（只拦登记过的类型）；
- spec.yaml 残缺或非法：记一条 warning 并跳过该类型，其它类型照常；
- 模板文件缺失：不报错，退化为从规则反推目标结构骨架；
- 匹配到多个 spec：按 priority 降序取首个命中；
- 自定义脚本抛错：只产出一条「函数执行失败」，不阻断其余规则。

| 规则写错导致误拦 | 中 | 高 | 非法 spec 跳过，配合 file_check 巡检与示例零违规守护 |

## 常见问题

### 客户 FAQ

- **它替掉什么？** 替掉写进 prompt 的格式要求，以及评审阶段人肉挑缺章节。
- **它不做什么？** 不评内容好坏、不做跨文档一致性、不替换宿主 write/edit。
- **对现有工作流有什么影响？** 默认 diff_mode=delta，只拦本次新增的违规；存量文档不被追溯，无需迁移。

### 内部 FAQ

- **为什么是现在？** 试点 3 周 17 次格式打回，评审时间被结构问题吃掉，6 条自定义判据全被「要改插件」卡住。
- **为什么由插件层做？** 写文档的是 agent，校验必须挂在落盘链路上；prompt 约束无法机械验证。
- **最怕的问题是什么？** 项目方不愿维护 YAML。对策见风险表的最危险假设行。
- **要砍先砍哪块？** 先砍 functions 里的 script 逃生舱（保留 expr），再砍示例内联；核心只留声明式规则 + 结构原语。

## 备选方案

- 继续用写死的检查代码：接入新判据要改插件、发版，正是本期要解决的成本，不选；
- 纯 prompt 约束：模型自觉性不可靠，且无法机械验证，不选；
- 正则整篇匹配：表达不了「每个 H2 都要有 serves」这类结构判据，不选。

## 发布与回滚

按 workspace 灰度：先在试点项目用 warn 模式观察误报，再切成 block。
回滚只需把对应 spec 的 mode 改为 off，无需发版。插件本体升级走常规 bundle 安装。

- **可观测性**：每次 block 记结构化日志（spec / 规则 id / 违规数 / 耗时）；误报率超过 5% 触发告警并自动降级为 warn。
- **运维归属**：spec.yaml 由项目方维护；插件组负责引擎与内置原语；支持入口 = 插件仓库 issue。
