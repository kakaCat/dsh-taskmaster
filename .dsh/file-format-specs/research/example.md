# 内容格式校验子系统 调研报告

## 摘要  serves: 全文

- **调研问题**：给 dsh-file-enhance 增加「文档内容格式校验」子系统，是值得做、还是应该把它交给 prompt 纪律与人工评审？
- **办法**：研读宿主与插件源码（E-1）、在临时工作区跑通 4 组判据探针（E-2）、比对 Google / Amazon 的公开研究文档规范（E-3）、访谈 3 个项目组与 2 名评审人（E-4、E-5）。
- **结论**：**采纳**——判据数据化 + 落盘后校验的收益已被两个真实工作区验证（E-2、E-5）；但**不采纳**把校验做成「写入前阻塞」（E-6），并且必须接受「文件已落盘后才打回」这一取舍（见风险与不确定性）。
- **证据强度**：A 级 2 条、B 级 2 条、C 级 2 条、D 级 1 条；最大缺口是「跨团队规模效应」只有 2 个样本，见风险与不确定性。
- **这份调研不能用来决定什么**：不评价 UI / 交互形态，不做成本与排期估算，不覆盖非 markdown 文件类型。

## 背景与调研问题  serves: 全文

### 要不要查：决策背景

现有插件的路径子系统（`.dsh/folder-path-rules/`）已经解决了「文件放哪、叫什么」，但内容层面的问题原样留着：需求文档缺章节、PRD 的 FR 编号与明细对不上、指标没有埋点可追。今天的替代做法是在 prompt 里写一段「请遵循以下文档结构」，代价是三条：判据进不了版本控制（E-5）、模型每次都可能漏（E-4）、出了问题没有人能说清「哪条判据没过」。

要不要动，取决于一个具体判断：**内容判据能不能被机器判，以及判错的代价是否可接受**。前者决定有没有用，后者决定会不会变成每日噪音——所以这次调研只查这两件事，不查「要不要做可视化」这类产品形态问题。

### 调研问题清单

| 编号 | 调研问题 | 决策影响 | 影响程度 |
|---|---|---|---|
| Q-1 | 文档结构类判据（必备章节 / 表格列 / 编号连续性）能否在不引入自然语言理解的前提下机械判定？ | D-1：答否 → 整个子系统不立项 | 高 |
| Q-2 | 「落盘后校验并允许重试」与「写入前阻塞」两种接入方式，哪一种的总代价更低？ | D-2：决定接在 post-execute 还是 pre-execute | 高 |
| Q-3 | 判据数据化（放工作区 YAML）比内置在插件代码里，一次改判据的端到端成本差多少？ | D-3：决定 spec 是否放工作区、是否热重载 | 中 |
| Q-4 | 校验判据的误报会以什么形式、多大频率影响日常写作？ | D-1 / D-2：决定默认 severity 与 delta 归责策略 | 中 |

### 调研问题明细

#### Q-1 结构类判据能否机械判定

**调研问题**

在不使用大模型判定、只依赖文本结构解析的前提下，能否对「必备 H2 章节」「表格必备列」「编号连续与唯一」「frontmatter 字段」四类判据给出可复现的判定结果？

**决策影响**

D-1。答「能」则立项；答「不能」或「误判率高」则整条产品线不成立，退回到 prompt 纪律 + 人工评审的组合。

**调研与证据**

E-1（宿主 `PreToolDecision` / `PostToolDecision` 契约与 `write` 的 after 全文来源）、E-2（4 组探针：缺章节 / 缺列 / 编号跳号 / 值域越界全部被捕获，且代码围栏内的假结构未误伤）。

**反证与限定条件**

- 反证：语义类判据（「验收标准是否可验证」）无法机械判定——本结论只覆盖结构类，见风险与不确定性。
- 前提：文档解析必须先剥离代码围栏，否则 `## 假标题` 会造成系统性误判（E-2 第 2 组探针就是这条）。

#### Q-2 落盘后校验与写入前阻塞的代价对比

**调研问题**

在宿主现有工具契约下，两种接入方式各需要多少改动、对 agent 的往返次数与最终文件状态分别有什么影响？

**决策影响**

D-2。决定校验挂在 `tools/post-execute`（落盘后）还是 `tools/pre-execute`（落盘前），也决定 agent 是按「一次写对」还是「写错再改」工作。

**调研与证据**

E-1（`pre-execute` 只能 allow / deny / cancel / ask，且 `exec.arguments` 深度冻结，插件无法改写 `file_path`）、E-3（Google 研究文档规范与 Amazon 的 FAQ 结构都以「先写出草稿再按清单收敛」为工作方式）、E-6（工程判断：内容判据需要看到全文才能判，而 `pre-execute` 阶段拿不到 after 全文）。

**反证与限定条件**

- 反证：若宿主将来允许插件改写工具入参，「写入前纠正」的成本会降到与落盘后接近，本结论需要复议（E-1 的接口契约是唯一依据）。
- 代价必须显式接受：落盘后打回意味着**不合规的文件已经写在磁盘上**，重试期间其他人可能读到半成品。

#### Q-3 判据数据化与内置代码的成本差

**调研问题**

一次「项目想加一条自己的判据」的操作，从规则住工作区 YAML（热重载）与规则住插件源码（构建 + 重装 + 重启）两种形态看，端到端耗时与回归风险分别是多少？

**决策影响**

D-3。决定 spec 是否放 `.dsh/file-format-specs/`、是否需要 mtime 热重载、是否需要 `file_propose` 这类自助入口。

**调研与证据**

E-4（某团队把 6 条文档结构要求写进 prompt，两周内 3 次因模型漏读在第 12 节之后开始出现缺章节）、E-5（访谈记录：判据进 prompt 后无法 review、无法回归）。

**反证与限定条件**

- 前提：YAML 规则的表达力足够覆盖项目判据；表达力不足时必须留逃生舱（`expr` / `script`），否则团队会退回改代码。

#### Q-4 误报的形态与频率

**调研问题**

在真实写作节奏下，结构类判据打回里有多少是「真错」、多少是「作者有意为之」，分别出现在什么阶段？

**决策影响**

D-1 / D-2。决定默认 `diff_mode`（delta 还是 strict）、`max_attempts`、`on_exhausted`，以及是否保留 warning 级别。

**调研与证据**

E-4（3 个项目组的补写记录与评审意见：多数缺失出现在文档后半段，属于写到最后赶工）、E-5（评审人指出的历史遗留文档问题不应由本次编辑背锅，这条直接支持 delta 归责）。

**反证与限定条件**

- 限定：只有 2 个团队的样本，规模效应未验证；跨团队结论按低可信度处理。
- 反证：若作者频繁「有意偏离」判据，说明判据本身过严，应改 spec 而不是放宽校验。

## 调研方法与范围界定  serves: 全文

| 方法 | 具体做法 | 样本与规模 | 时间窗 | 局限 |
|---|---|---|---|---|
| 文档与源码研读 | 逐个读宿主工具契约、`write`/`edit` 结果结构、插件的判定链实现，记为 E-1 | 宿主 1 份 + 插件 2 个子系统 | 2026-10-13 ~ 2026-10-14 | 只覆盖当前版本，接口变更后需复议 |
| 原型实测 | 在临时工作区构造 4 组文档，跑判据探针并记录通过 / 打回结果与行号 | 4 组 × 每类 2 个变体 | 2026-10-14 | 探针由作者构造，可能偏向已知判据 |
| 规范比对 | 比对 Google、Amazon 的公开文档结构要求，看章节集合是否有共识 | 3 份公开规范 | 2026-10-14 | 均为大厂场景，团队规模差异未控制 |
| 访谈 | 半结构化访谈 3 个项目组 + 2 名评审人，逐条记录原文 | n = 5 | 2026-10-14 ~ 2026-10-15 | 样本量小，无问卷量化 |
| 竞品试用 | 试用 2 个文档 lint 工具，观察其对语义类判据的处理 | 2 个工具 | 2026-10-15 | 只做定性比较 |

**范围界定**

- **纳入**：markdown 文档的结构类判据、`write` / `edit` 两个入口、单工作区内的规则分发。
- **排除**：自然语言语义判据、非 markdown 文件、跨仓库规则共享——成本高且与本决策无关。
- **不做的事**：不做成本与排期估算，不评价 UI，不给出「组织是否愿意维护判据」的判断。

## 关键发现  serves: Q-1

| 编号 | 发现 | 支撑证据 | 事实或推断 | 可信度 |
|---|---|---|---|---|
| F-1 | 四类结构判据（章节 / 表格列 / 编号 / frontmatter）可机械判定，且解析器剥离代码围栏后无系统性误报 | E-2 | 事实 | 高 |
| F-2 | 宿主 `pre-execute` 只提供四档决策且入参冻结，插件无法在写入前改写路径或内容 | E-1 | 事实 | 高 |
| F-3 | 结构判据写在 prompt 里会随文档长度衰减，缺失集中在长文档后段 | E-4 | 推断 | 中 |
| F-4 | 历史遗留文档的旧违规必须与本次编辑分离，否则校验会被当成噪音关掉 | E-5 | 推断 | 中 |
| F-5 | 「写入前纠正」在现有契约下不可行，落盘后打回是当前唯一可行接入点 | E-1、E-6 | 推断 | 中 |

### 与直觉相反的地方

最初假设是「阻塞式校验（写入前拦下）体验更好」，调研推翻了它：`pre-execute` 阶段既拿不到全文、也无法改写入参（E-1），阻塞式只能退化成「写一次、拒一次、再写一次」的两倍往返；反而是落盘后打回 + 目标模板注入能让 agent 一次改对（F-5）。

## 方案对比矩阵  serves: Q-2

| 评估维度 | 权重 | 判据数据化 + 落盘后校验 | 判据内置 + 写入前阻塞 | 维持现状（prompt 纪律） | 标注 |
|---|---|---|---|---|---|
| 判据可表达性 | 30% | 4 / 5（结构类全覆盖，语义类需脚本逃生舱） | 4 / 5（同等表达力） | 1 / 5（不可机械判定） | E-1、E-2 |
| 一次改对的往返次数 | 25% | 4 / 5（打回时附目标模板） | 2 / 5（拿不到全文，需两次往返） | 2 / 5（靠模型自觉，长文衰减） | E-1、E-3 |
| 判据可维护性 | 20% | 5 / 5（工作区 YAML，改文件即生效） | 2 / 5（改代码 + 构建 + 重装） | 1 / 5（进不了版本控制） | E-5 |
| 评审与回归友好度 | 15% | 5 / 5（判据可 review、可 delta 归责） | 5 / 5 | 1 / 5 | E-5 |
| 落地成本与风险 | 10% | 3 / 5（新增子系统，但只读 post 钩子） | 2 / 5（需要宿主改契约，跨团队协作） | 5 / 5（零成本，问题原样保留） | E-6 |

## 结论与建议  serves: 全文

| 决策编号 | 结论 | 立场 | 成立条件 | 翻转条件 |
|---|---|---|---|---|
| D-1 | 立项内容格式校验子系统：判据数据化 + 落盘后校验 | 采纳 | 结构类判据足够覆盖团队诉求；宿主保留 post-execute 钩子与 after 全文 | 出现「结构判据无法覆盖、语义判据才是主要痛点」的实测证据 |
| D-2 | 校验接 `tools/post-execute`，默认 `diff_mode: delta`，`max_attempts: 3`，用尽后放行 | 采纳 | `pre-execute` 仍然不可改写入参、不可读全文 | 宿主开放入参改写，或 delta 归责被证明会漏掉真实违规 |
| D-3 | spec 放工作区 `.dsh/file-format-specs/`，按 mtime 热重载 | 采纳 | 规则作者就是项目成员，愿意用 YAML 表达判据 | 判据复杂度超出 YAML + 脚本表达力，团队退回改代码 |

**不采纳的方案与理由**

- **写入前阻塞式校验**：`pre-execute` 阶段拿不到全文、无法改写入参，只能退化成两次往返（E-1、E-6）。
- **把判据继续留在 prompt 里**：长文档后段系统性缺失，且判据无法 review 与回归（E-4、E-5）。
- **内置一套「默认判据」随插件分发**：判据的权威必须属于项目自己，否则项目会用「改判据」代替「改文档」（E-5）。

## 风险与不确定性  serves: 全文

**最危险假设**

- 假设「结构类判据就是团队的主要痛点」。如果实际痛点在语义（例如「验收标准是否可验证」），本子系统的收益会大幅缩水——最便宜的证伪方式是在两个真实工作区各跑两周，统计打回里结构类与语义类的比例。

| 信息缺口 | 影响哪个结论 | 获取成本 | 处理方式 |
|---|---|---|---|
| 只有 2 个团队的样本，跨团队规模效应未验证 | D-1 | 约 3 人日（再访谈 5 个团队） | 下次补；在此之前 D-1 只作为「值得试点」的结论使用 |
| 探针由规则作者自己构造，可能存在「只测了已知判据」的偏差 | D-1 | 约 1 人日（引入第三方判据清单） | 本次接受不确定性，写明失效条件：出现探针未覆盖的结构判据被误判时复议 |
| 宿主未来若开放工具入参改写，D-2 的成本对比会变 | D-2 | 无（等待宿主变更） | 下次补；E-1 契约一变即触发复议 |
| 非 markdown 类型的诉求未调研 | D-1 | 约 2 人日 | 本次明确排除，不纳入结论 |
